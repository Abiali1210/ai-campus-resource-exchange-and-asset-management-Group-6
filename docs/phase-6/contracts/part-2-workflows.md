# Part 2 request and transfer contracts

Scope: C4–C6. This extends the [foundation](part-1-foundation.md) and implements
relevant portions of SRS FR-REQUEST-001–008 / FR-TRANSFER-001–008, UC-04/07/08, BR-003/005/006/007
and design v1.4 Sections 5, 9–11. No AI or reporting module is introduced.

This is the C4–C6 minimum, not completion of every SRS refinement. Optional
purchase-basis indication (FR-REQUEST-008), combined approval UI and the Business
Administrator escalation screen (FR-TRANSFER-008) remain deferred. Unresolved stock
stays disputed/allocated pending authorized full reconciliation or confirmed return.

## Architecture and authority

`WorkflowService` extends the existing Supabase service class. `WorkflowPanel`
provides the forms and tracking screens. PostgreSQL owns the business rules;
React controls help users choose actions but confer no permission.

New tables are `resource_requests`, `interests`, `reservations`, `transfers`,
`approvals` and `handovers`. Ordinary callers have no direct table privileges;
row level security is enabled and internal helpers are not callable by API roles.
The existing audit, committed-event and operation-result tables are reused.

An active Requester/Representative can submit a need for their own department.
Its requester with a current Requester/Representative role, and the department's
Representative, can track and select stock. Supplier Representatives see needs
linked to their own department's Interests/transfers only. Assigned active
Facilities see their transfers and associated request. Technical or Business
Administrator status alone grants no workflow approval or mutation authority.

Each Interest stores its **original supplier department**, independent of later
stock ownership. A new owner cannot read or decide old competing Interests.
Both reservation and release decisions reject an actor who is the requester or
Interest creator, including users with several roles. One supplier representative
may make both decisions when that person is neither requester nor Interest creator.

## Public operations

`workflow_workspace()` returns caller-scoped camel-case `requests`, `interests`,
`transfers`, `facilities`, `decisions`, and `history`. Nested persisted approval
and handover records retain SQL column names; their TypeScript interfaces are in
`src/workflows.ts`. Transfer holder options contain only active participating
Representatives, receiving Requesters and the assigned Facilities person.
Asset financial values and unrelated workflow records are excluded.

`workflow_command(p_input jsonb)` accepts one action per transaction. Every
command requires an `operationKey` UUID, generated by the client and retained for
retry. Consequential actions and Interest selection require a nonempty `reason`.

| Action                           | Input beyond action, operationKey and reason                                                                    | Authorized actor / effect                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `submitRequest`                  | purpose, categoryId, qty, specifications object, condition, urgency, requiredDate, destination; reason optional | Requester/Representative; requester/department come from authenticated profile                                             |
| `recordInterest`                 | requestId, expectedVersion, portionId, qty                                                                      | Own requester / receiving department Representative; creates Interest only                                                 |
| `approveReservation`             | interestId, expectedVersion, qty                                                                                | Original supplier Representative, never self; commits allocation and Pending Approval transfer                             |
| `rejectReservation`              | interestId, expectedVersion                                                                                     | Original supplier Representative, never self; separate rejected decision, no allocation                                    |
| `approveRelease`                 | transferId, expectedVersion, facilitiesId                                                                       | Supplier Representative, never self; separate decision, assigns active Facilities                                          |
| `rejectRelease`                  | transferId, expectedVersion                                                                                     | Supplier Representative, never self; decision and pre-dispatch cancellation                                                |
| `schedule`                       | transferId, expectedVersion, scheduledAt ISO timestamp, arrangements, optional handlingCost/transportCost       | Assigned Facilities; future slot on/before required date (Dubai calendar), nonnegative AED costs                           |
| `dispatch`                       | transferId, expectedVersion, qty, location                                                                      | Assigned Facilities; full approved quantity, safe scheduled stock, holder becomes actor                                    |
| `receive`                        | transferId, expectedVersion, qty, condition, accept boolean, location, optional holderId                        | Receiving Representative; full suitable acceptance completes, otherwise records dispute                                    |
| `reconcile`                      | same as receive, accept=true                                                                                    | Receiving Representative; disputed transfer, full suitable quantity only                                                   |
| `confirmReturn`                  | transferId, expectedVersion, qty, condition, location, optional holderId                                        | Supplier Representative; disputed transfer, full reconciled physical return only                                           |
| `cancelTransfer`                 | transferId, expectedVersion                                                                                     | Requester / receiving or supplying Representative; before dispatch only                                                    |
| `closeRequest` / `cancelRequest` | requestId, expectedVersion                                                                                      | Own requester / receiving Representative; no active allocations; accepted partial need must be closed rather than canceled |

Minimum request condition is Excellent, Good or Fair. Mandatory specifications use
exact JSON containment, including value types: `{"connector":"HDMI"}` requires that
recorded evidence. Unknown, Poor, missing or incompatible mandatory evidence blocks
reservation. This deliberately conservative rule gives Part 3 a predictable gate;
semantic similarity cannot establish missing suitability evidence. Urgency does not
automatically win stock: the supplier reviews submission order and records the reason
for its decision, including any departure for urgency, suitability or timing.

The result contains the created `requestId`, `interestId`, or `transferId`, relevant
`reservationId`, and version. Failures use the existing database message prefixes
`Unauthorized`, `Forbidden`, `Validation` and `Conflict`. Reload after Conflict.
An unchanged retry with the same key returns the original result; changing the
payload under that key is a Conflict. `WorkflowOperation` retains a cloned payload
through uncertain network responses while the form is mounted. Browser refresh
does not persist that key: reload tracking before submitting again after a refresh.

The new overload `asset_detail(p_asset_id,p_portion_id)` returns the selected,
authorized active leaf and its permitted history. The legacy one-argument contract
remains available. The frontend passes the selected portion after batch splitting.

## Quantities and state transitions

For each request:

```text
acceptedQty  = sum(reservation.qty where status = Accepted)
allocatedQty = sum(reservation.qty where status = Active)
remainingQty = requestedQty - acceptedQty - allocatedQty
```

No client can edit these totals. Interest does not change them. A reservation's
composite foreign key ties its request and source portion to its Interest. The
allocated `portion_id` can differ from `source_portion_id` after splitting. Partial
approval closes the parent and creates Reserved/Available children whose quantities
sum to the parent. Whole approval reuses the leaf. A unique index allows only one
active reservation per leaf. Existing deferred stock-conservation constraints check
the sum of active leaves at commit. Inactive parents remain historical lineage.

Each mutation locks request, asset, portion, then Interest/transfer in that order.
After acquiring locks it rechecks current state, suitability and both quantity
limits. The request lock serializes competing allocations across different assets;
the asset/portion locks serialize different requests for the last stock unit.
No network/AI call occurs while these locks are held.

The losing Interest on a split parent is retained. It cannot automatically follow
the remainder: select the current Available child for a new Interest. Approved
quantity cannot exceed selected quantity. An unapproved part of a selected Interest
also requires a new Interest. Cancellation leaves conserved fragments rather than
merging historical portions.

Transfer states are Pending Approval → Approved → Scheduled → In Transit →
Completed. A receipt discrepancy moves In Transit → Disputed. Reconciliation can
move Disputed → Completed, and supplier-confirmed return moves Disputed → Returned.
Pending Approval/Approved/Scheduled can be Canceled; moved/disputed stock cannot.
Rescheduling is allowed before dispatch with the current version.

Dispatch changes holder/physical location only. Full suitable accepted receipt
changes formal owner department, custodian and assigned location together with
fulfillment. Observation authority and physical possession are separate: `holderId`
may identify an active participant; omission defaults to the observing actor.
Receipts record actual observations even when the user tried to accept a short or
unsuitable delivery. Disputed quantity stays actively allocated and unavailable.
Reconciliation and return append distinct handovers; they never erase observations.

Full confirmed return releases allocation and restores remaining demand without
adding accepted fulfillment. Good/Excellent/Fair returned stock becomes Available;
Unknown becomes Registered and Poor becomes Unfit. An unresolved short return cannot
release allocation. Cancellation preserves unsafe/non-Reserved states and never
clears an unsafe assessment. No maintenance or end-of-life endpoint is added.

Terminal transfer tracking is frozen in `tracking_snapshot`, so an earlier requester
or supplier cannot observe later unrelated movement of the reused portion. Active
transfers use current physical tracking. History retains actor, UTC time, reason,
before/after data and operation key; its audit and committed event commit in the
same transaction as the mutation. Failure to persist audit rolls back the mutation.

## Contracts for later owners

Part 3 must use `recordInterest` for human match selection and
`approveReservation` for ordinary human allocation. Read remaining demand from
authoritative projections; do not count Interest as stock allocation. Category,
safe condition and mandatory-specification gates must survive any AI outage.

Part 4 can calculate accepted units from Accepted reservations / Completed
transfers. Count transfer events separately from accepted units. Canceled/Returned
allocations do not count as accepted, and Disputed remains pending. Closed requests
can retain a positive historical remainingQty; do not count that as open demand.
Handling/transport costs are optional AED values: null means unrecorded, not zero.
This data contract does not implement the report or any claimed savings measure.

Seven [fixture recipes](../../../tests/fixtures/workflows.json) include open need,
Interest without allocation, pending release, scheduled movement, partial accepted
and allocated need, dispute and unsafe confirmed return. Their expected totals are
checked by both PostgreSQL test engines. See the [handoff](../handoffs/02-ahmed.md)
for setup, actual verification and service limitations.
